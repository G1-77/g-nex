The One Big Conflict
The inflation badge shows red when portfolio is below inflation. The existing code renders a red badge when growth is negative or below 5.1%. The proposal explicitly says: never show the badge when below — don't shame the user. This is the only direct conflict between the existing implementation and the proposal. Everything else is either aligned or a gap (missing feature), not a contradiction.

Fix: in the growth badge component, add if (growthPct < 0) return null and change the below-inflation state from red to amber rather than hiding entirely — amber says "almost there" which is motivating, red says "you failed" which is not.

Remove fake performance chart or replace with real data
A seeded PRNG chart in a financial app is a critical trust issue. Users will notice the chart looks identical every time they open the app. Either remove the PerformanceArea component entirely and replace with a simple "portfolio value today" stat, or wire it to real trade history from the orders table. Do not ship fake data.

Fix inflation badge — hide when below, amber when close

Sell currently routes to a 404. This must be fixed before any user tries to sell an asset. The sell action should either open a modal on the asset page or route to /markets/[symbol] with a ?action=sell query param that opens the trade panel pre-selected to Sell.
P0 — Broken feature 404 on sell
5
Build the admin deposit approval flow
This is the core of Phase 1. Without it, deposits submitted by users are never credited. The admin needs: a page listing pending deposit_requests rows, a Confirm button that calls a server action to update status → 'confirmed' + increment balance_kes + insert a notification row for the user. This is the most important missing piece for the platform to actually function.
// Server action: confirmDeposit(depositId) await supabase.from('deposit_requests') .update({ status: 'confirmed', reviewed_by: adminId, reviewed_at: new Date() }) .eq('id', depositId) await supabase.from('user_wallets') .update({ balance_kes: supabase.rpc('increment', { amount: depositAmountKes }) }) .eq('user_id', userId) await supabase.from('notifications').insert({ user_id: userId, type: 'deposit_confirmed', title: 'Deposit Confirmed ✓', body: `KES ${amount} added to your wallet.` })
P1 — Platform cannot function without this
6
Wire notification inserts on deposit submit
When POST /api/deposits succeeds, insert a notifications row immediately: type: 'deposit_pending', title: 'Deposit Under Review', body: 'KES X is being verified'. This powers the bell badge via Supabase Realtime. Currently the success screen exists but no notification row is created.
P1 — Required for two-notification pattern
7
DB-lock withdrawal balance on submission
Currently balance_kes is never decremented — only a UI soft lock from summing pending withdrawal rows. If user closes app and returns, the pending row still soft-locks correctly. However the actual DB balance_kes stays high, which means an admin viewing raw data sees inflated balances. Add a locked_kes column to user_wallets and increment it on withdrawal request submission, decrement on rejection, zero on completion.
// user_wallets schema addition: locked_kes numeric DEFAULT 0 // On withdrawal submit: locked_kes += withdrawalAmount // available_kes computed as: available = balance_kes - locked_kes

Also add the mpesa_reference column to deposit_requests now so Phase 2 Daraja requires zero migrations.
